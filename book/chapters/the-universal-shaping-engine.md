# The Universal Shaping Engine

The **Universal Shaping Engine** (**USE**) is Microsoft’s answer to a problem of numbers. Unicode encodes dozens of scripts built like Devanagari, a consonant with marks above, below and around it, and each dedicated shaper like the Indic one in [the last chapters](the-indic-model.html) took years of script-by-script rules. USE replaces the rules with data: every character gets a class derived from Unicode’s properties, one grammar says which sequences make a cluster, and one short reordering step moves the few things that must move. Microsoft announced it in 2015, and HarfBuzz implemented it in version 1.0.0, whose `NEWS` links to Microsoft’s specification and its announcement.

HarfBuzz’s USE is the Indic model with most of the model taken out. It keeps the four parts: categories from a generated table, syllables from a Ragel machine, GSUB features in stages with pauses between them, and a reordering pass. It drops the base consonant, the positions, the questions put to the font, the per-script table and the second reordering. What is left is about 500 lines of C++ (`hb-ot-shaper-use.cc`) and a 300-line grammar, and they serve 91 scripts, from Tibetan to the Unicode 18.0 additions, as well as the nine Indic scripts when a font uses their `3` tags ([Choosing a script shaper](choosing-a-script-shaper.html#from-tags-to-a-shaper)).

The examples use two families of test fonts with plain boxes for glyphs, built by `fonts/the-universal-shaping-engine/build-fonts.py`. The Devanagari fonts come in pairs, compiled from one feature file under `dev2` (the Indic shaper) or `dev3` (USE): `deva2.ttf` and `deva3.ttf` have lookups for `rphf`, `akhn`, `blwf`, `half`, `init` and `pres`; the `-half-first` pair has the same lookups with `half`’s first in the LookupList; the `-no-half` pair has no `half`. `balinese.ttf` has a few Balinese letters and signs, and a `blwf` that makes two subjoined consonants; `balinese-no-blwf.ttf` doesn’t. Every result and trace on this page was produced by running HarfBuzz {{hb}} on them when the page was built.

## What USE keeps, and what it drops

| | Indic shaper | USE |
|---|---|---|
| table | category and position, from three Unicode files | one category, positions folded in, from nine files |
| syllables | Ragel scanner, six types | Ragel scanner, nine types, over a filtered buffer |
| base consonant | searched for, from the font’s answers | none |
| basic features | one stage each, with masks set by the reordering | all in one stage, on the whole syllable, except `rphf` and `pref` |
| reordering | initial (sort by position) and final (reph, pre-base vowels, `pref`) | one pass after the basic features: reph forward, pre-base glyphs back |
| per-script rules | a configuration table and many `if`s | none |
| `init` | a pre-base vowel sign at the start of a word | a topographical form of a whole cluster |
| mark widths | not zeroed | zeroed from GDEF, before GPOS |

The rest of this chapter takes those rows in turn.

## Categories

`setup_masks_use` (`hb-ot-shaper-use.cc:189`) looks each character up with `hb_use_get_category` and keeps the answer in the scratch byte `use_category` ([Buffers](buffers.html#eight-bytes-of-scratch-space)). There is no position byte. Where the Indic table gives a vowel sign a category and a position, USE folds the position into the category: a vowel sign is `VPre`, `VAbv`, `VBlw` or `VPst`.

### Where they come from

`hb-ot-shaper-use-table.hh` is generated by `gen-use-table.py` from nine files (`update-unicode-tables.make:37`). Seven are Unicode’s: `IndicSyllabicCategory.txt`, `IndicPositionalCategory.txt`, `ArabicShaping.txt` (for joining types), `DerivedCoreProperties.txt` (for default ignorables), `UnicodeData.txt` (for general categories), `Blocks.txt` and `Scripts.txt`. Two are Microsoft’s: `ms-use/IndicSyllabicCategory-Additional.txt` and `ms-use/IndicPositionalCategory-Additional.txt`, MIT-licensed and maintained by Andrew Glass, whose headers record an update for every Unicode version since 7.0, the last “for Unicode 18.0 … 2026-09-04”. The generated header records version 18.0.0 of every Unicode file but one: `DerivedCoreProperties.txt` is 17.0.0.

The Microsoft files do two things. They override Unicode’s values where they don’t suit shaping, each with its reason: DOTTED CIRCLE is a `Consonant`, “Reassigned to allow it to cluster as a generic base”; TIBETAN VOWEL SIGN I is `Bottom`, “Not really below, but need to override to fit into Universal model”. And they give values to scripts that Unicode’s Indic properties don’t cover at all, such as Mongolian, N’Ko, Adlam and the Egyptian hieroglyph format controls.

The generator reads the files into one record per code point (`:59`–`:108`), and drops five scripts that never reach USE, `DISABLED_SCRIPTS` (`:40`): Arabic, Lao, Samaritan, Syriac and Thai. A character in no file is `O`. Then, for each character, it asks a list of predicates, `is_BASE`, `is_HALANT` and so on, which follow the derivations in Microsoft’s specification, and asserts that exactly one says yes (`map_to_use`, `:382`). If the category has positions, a suffix from the positional category is added (`use_positions`, `:334`): `Top` gives `Abv`, `Bottom` or `Overstruck` `Blw`, `Right` `Pst`, `Left` `Pre`. A vowel sign in two or three places takes the first of pre, above and below that it has a part in: `Left_And_Right` is `VPre`, `Top_And_Bottom` `VAbv`, `Bottom_And_Right` `VBlw`.

The predicates don’t follow the specification everywhere. The differences, with what the source says of each:

## Syllables

The first GSUB pause, before any lookup, finds the syllables (`setup_syllables_use`, `hb-ot-shaper-use.cc:297`), marks each one unsafe to break, and sets two kinds of mask, for `rphf` and for the topographical features, both described below. `found_syllable` writes the type and a serial number into the `syllable` byte, exactly as the Indic machine does ([Finding syllables](the-indic-model.html#finding-syllables)), and `foreach_syllable` hands out at most 64 glyphs at a time ([A limit on syllable length](the-indic-model.html#a-limit-on-syllable-length)). Microsoft’s specification gives “a practical maximum cluster length” of 31 characters.

### The grammar

The grammar, trimmed of the hieroglyph and number rules (`hb-ot-shaper-use-machine.rl:114`):

```
h = H | HVM | IS | Sk;

consonant_modifiers = CMAbv* CMBlw* ((h B | SUB) CMAbv* CMBlw*)*;
medial_consonants = MPre? MAbv? MBlw? MPst?;
dependent_vowels = VPre* VAbv* VBlw* VPst* | H;
vowel_modifiers = HVM? VMPre* VMAbv* VMBlw* VMPst*;
final_consonants = FAbv* FBlw* FPst*;
final_modifiers = FMAbv* FMBlw* | FMPst?;

complex_syllable_start = (R | CS)? (B | GB);
complex_syllable_middle =
	consonant_modifiers
	medial_consonants
	dependent_vowels
	vowel_modifiers
	(Sk B)*
;
complex_syllable_tail =
	complex_syllable_middle
	final_consonants
	final_modifiers
;
symbol_cluster_tail = SMAbv+ SMBlw* | SMBlw+;

virama_terminated_cluster_tail = consonant_modifiers (IS | RK);
virama_terminated_cluster = complex_syllable_start virama_terminated_cluster_tail;
sakot_terminated_cluster_tail = complex_syllable_middle Sk;
sakot_terminated_cluster = complex_syllable_start sakot_terminated_cluster_tail;
standard_cluster = complex_syllable_start complex_syllable_tail;
tail = complex_syllable_tail | sakot_terminated_cluster_tail | symbol_cluster_tail | virama_terminated_cluster_tail;
broken_cluster = R? (tail | number_joiner_terminated_cluster_tail | numeral_cluster_tail);
symbol_cluster = (O | GB | SB) tail?;
```

(Line breaks are trimmed.) Where the Indic grammar is built around how Indic syllables are spelt, this one is a single template, the specification’s “maximal cluster scheme”: an optional repha, a base, consonants joined to it by viramas or subjoined, then one medial in each place, vowel signs in the order pre, above, below, post, vowel modifiers in the same order, final consonants, and a final modifier. Each group is optional, and their order is fixed. A visible virama counts as a vowel sign, “Treat visible viramas like dependent vowels” (`NEWS` for 4.1.0), so a syllable can end in one. Every syllable may end in a ZWNJ (`:173`).

The syllable types, and what HarfBuzz does with each:

| Type | What it is | Reordered | Joins topographically |
|---|---|---|---|
| **standard cluster** | the template above | yes | yes |
| **virama-terminated cluster** | a base and its consonants, ending in an invisible stacker or reordering killer | yes | yes |
| **sakot-terminated cluster** | the same, ending in Tai Tham’s sakot | yes | yes |
| number-joiner-terminated, numeral | Brahmi numbers (U+11052 to U+11065) joined by U+1107F BRAHMI NUMBER JOINER | no | yes |
| symbol cluster | a space, symbol, punctuation or generic base, with any tail | yes | yes |
| hieroglyph cluster | Egyptian hieroglyphs and their format controls | no | no |
| broken cluster | a tail with no base | yes | yes |
| non-cluster | anything else, and a lone `FMPst` | no | no |

The order is strict. In Balinese, suku (below) may follow ulu (above), but not the other way round; and a final consonant such as surang comes after the vowel signs:

```shape
balinese.ttf  ᬓ\u1B36\u1B38  --language=ban
balinese.ttf  ᬓ\u1B38\u1B36  --language=ban
balinese.ttf  ᬓ\u1B38\u1B03  --language=ban
balinese.ttf  ᬓ\u1B03\u1B38  --language=ban
```

In the second and fourth lines, the syllable ends where the order breaks, and the mark left over is a broken cluster, given a dotted circle ([Dotted circles and broken clusters](dotted-circles-and-broken-clusters.html) covers that, and the vowel constraints that USE’s `preprocess_text` applies). Unicode’s canonical ordering doesn’t help: these signs all have combining class 0, so normalization leaves them as typed.

### What the machine doesn’t see

The machine doesn’t run over the buffer itself, but over a filtered view of it (`find_syllables_use`, `:258`), built from HarfBuzz’s iterators:

```c++
auto p =
  + hb_iter (info, buffer->len)
  | hb_enumerate
  | hb_filter ([] (const hb_glyph_info_t &i) { return not_ccs_default_ignorable (i); },
	       hb_second)
  | hb_filter ([&] (const hb_pair_t<unsigned, const hb_glyph_info_t &> p)
	       {
		 if (p.second.use_category() == USE(ZWNJ))
		   for (unsigned i = p.first + 1; i < buffer->len; ++i)
		     if (not_ccs_default_ignorable (info[i]))
		       return !_hb_glyph_info_is_unicode_mark (&info[i]);
		 return true;
	       })
  | hb_enumerate
  | machine_index
  ;
```

The first filter drops every `CGJ`, so CGJ, ZWJ and the variation selectors can stand anywhere: the specification says CGJ “may occur anywhere in a cluster with no effect”. The second drops a ZWNJ that is followed, past any of those, by a mark: such a ZWNJ continues the cluster instead of ending it, as the specification says it should. The syllable types are then written back over the ranges of original indices, so the hidden characters get the syllable of their neighbours. A ZWNJ between KA and suku doesn’t leave the suku without a base:

```shape
balinese.ttf  ᬓ\u1B38  --language=ban
balinese.ttf  ᬓ\u200C\u1B38  --language=ban
```

(The ZWNJ is shown as the font’s space glyph with no advance, as HarfBuzz shows every default ignorable it keeps.)

### Spaces as bases

A symbol cluster starts with `O`, `GB` or a hieroglyph bracket, and may take “any non-numeric tail” (`NEWS` for 4.0.1). Since `O` is also the space, a vowel sign after a space has a base, gets no dotted circle, and a pre-base one is moved before the space:

```shape
deva2.ttf  क \u093F  --language=hi
deva3.ttf  क \u093F  --language=hi
balinese.ttf  \u0020\u1B3E  --language=ban
```

The Indic shaper shows the stray vowel sign on a dotted circle; USE draws it on the space, or before it. The specification has an **independent cluster** for `O`, which takes nothing but a variation selector, and a symbol cluster only for symbols (`S`) and generic bases; HarfBuzz has merged the specification’s `O`, `IND` and `S` into one category (`gen-use-table.py:271`), and so they all take marks. That looks unintended for spaces (inferred: the source gives no reason).

## Features and stages

`collect_features_use` (`hb-ot-shaper-use.cc:110`) lays out the stages, under the names of the specification’s groups:

| Stage | Features | Pause after it |
|---|---|---|
| after `rvrn`’s | the direction features, `frac`, `numr`, `dnom`, `rand`, `Harf`, `HARF` | `setup_syllables_use` |
| “Default glyph pre-processing group” | `locl`, `ccmp`, `nukt`, `akhn` | `_hb_clear_substitution_flags` |
| “Reordering group” | `rphf` | `record_rphf_use`, then `_hb_clear_substitution_flags` |
| | `pref` | `record_pref_use` |
| “Orthographic unit shaping group” | `rkrf`, `abvf`, `blwf`, `half`, `pstf`, `vatu`, `cjct` | `reorder_use`, then `hb_syllabic_clear_var` |
| “Topographical features” | `isol`, `init`, `medi`, `fina` | none |
| “Standard typographic presentation” | `abvs`, `blws`, `haln`, `pres`, `psts`; then `Buzz`, `BUZZ`, the common and horizontal features, and the application’s | |

([From features to lookups](from-features-to-lookups.html#stages-and-pauses) explains `rvrn`, `Harf` and `Buzz`.) Within each group, lookups run in LookupList order, whatever their features. The specification says so: “it is, therefore, up to the font developer to specify the order of lookups for these features in the font’s OTL. The order given here is recommended but not required.” Only `rphf` and `pref` have stages of their own, because what each did must be recorded before the next.

The flags differ from the Indic shaper’s too:

* Every feature up to the reordering is per syllable, but the topographical and presentation features are not: the syllables have been released before they run. An Indic font’s `pres` cannot ligate across syllables; a USE font’s can. `deva2.ttf` and `deva3.ttf` have a `pres` ligature of TA + TA, here two syllables:

```shape
deva2.ttf  तत  --language=hi
deva3.ttf  तत  --language=hi
```

* `akhn`, `rphf`, `pref`, the basic and the presentation features have `F_MANUAL_ZWJ`, so their input doesn’t pass over ZWJ, but not `F_MANUAL_ZWNJ`: a rule’s backtrack and lookahead pass over ZWNJ ([Joiners](gsub.html#joiners)). The Indic shaper sets both.
* `rphf` and the topographical features are added with `add_feature`, so they have mask bits and apply only where the shaper sets them. Everything else is on everywhere: there is no mask for `half`, `blwf` or `pstf`, because there is no base to say which consonants should take them.
* `liga` stays on. The Indic shaper turns it off.

The shaper zeroes the advances of GDEF marks before GPOS (`HB_OT_SHAPE_ZERO_WIDTH_MARKS_BY_GDEF_EARLY`, `:509`), “what Windows does” (`NEWS` for 1.2.0); the Indic shaper zeroes none. Its normalization is the Indic shaper’s, with one rule in `compose_use` (`:482`), “Avoid recomposing split matras”, explained in [Normalization](normalization.html). So a split vowel sign such as Balinese taling tedung, U+1B40, is always split into taling and tedung, and taling moves:

```shape
balinese.ttf  ᬓ\u1B40  --language=ban
```

## Reordering

USE reorders once, after the basic features, and only three kinds of glyph move: a reph, which moves forward, and pre-base vowel signs and pre-base vowel modifiers, which move back. Nothing is sorted. What counts as a reph or a pre-base form is decided by the categories, or by what the font’s `rphf` and `pref` lookups did.

### What the font did

Before any lookup, `setup_rphf_mask` (`:213`) gives the `rphf` bit to the first three glyphs of each syllable, or only to the first if it is an encoded repha (`R`). The three are the specification’s: “Feature application is scoped to the first three glyphs in a cluster.” After `rphf`, `record_rphf_use` (`:311`) finds the first glyph in that prefix that a substitution produced, and makes it `R`. The pause before `rphf` cleared every glyph’s substituted flag, so only `rphf`’s own work counts. In `deva3.ttf`, `rphf` ligates RA and virama, and the ligature is `R` from then on.

`pref` is on for the whole syllable. `record_pref_use` (`:335`) makes the first glyph in each syllable that `pref` substituted a `VPre`, “as they behave the same way”. The specification’s example is Javanese, which “may reorder a medial consonant to the beginning of a cluster based on context”, and leaves the context to the font.

### The move

`reorder_syllable_use` (`:362`) skips number, hieroglyph and non-clusters. Then:

```c++
/* Move things forward. */
if (info[start].use_category() == USE(R) && end - start > 1)
{
  /* Got a repha.  Reorder it towards the end, but before the first post-base
   * glyph. */
  for (unsigned int i = start + 1; i < end; i++)
  {
    bool is_post_base_glyph = (FLAG64_UNSAFE (info[i].use_category()) & POST_BASE_FLAGS64) ||
			      is_halant_use (info[i]);
    if (is_post_base_glyph || i == end - 1)
    {
      if (is_post_base_glyph)
	i--;

      buffer->merge_clusters (start, i + 1);
      /* ... move info[start] to i ... */
      break;
    }
  }
}

/* Move things back. */
unsigned int j = start;
for (unsigned int i = start; i < end; i++)
{
  uint32_t flag = FLAG_UNSAFE (info[i].use_category());
  if (is_halant_use (info[i]))
    j = i + 1;
  else if (((flag) & (FLAG (USE(VPre)) | FLAG (USE(VMPre)))) &&
	   /* Only move the first component of a MultipleSubst. */
	   0 == _hb_glyph_info_get_lig_comp (&info[i]) &&
	   j < i)
  {
    buffer->merge_clusters (j, i + 1);
    /* ... move info[i] to j ... */
  }
}
```

(trimmed). A **post-base glyph** is any final, medial or vowel sign, any vowel modifier (`POST_BASE_FLAGS64`, `:377`), or a virama that wasn’t ligated (`is_halant_use`, `:355`, which counts `H`, `HVM` and `IS` but not the sakot). A reph moves forward past everything else, bases, half forms and subjoined forms, and stops before the first post-base glyph, or goes to the end. A pre-base vowel sign or modifier moves back to the start of the syllable, or to just after the last unligated virama before it. Each move merges the clusters it passes. This is the specification’s rule that “reordering components do not reorder past an explicit virama”, and its advice follows: a font that wants the reph or vowel sign to pass a virama should ligate or replace the virama during the basic features.

Balinese shows the virama rule. The adeg-adeg is a virama, and with `blwf` it is ligated into the subjoined form of TA; without, it stays:

```shape
balinese.ttf  ᬓ\u1B44ᬢ\u1B3E  --language=ban
balinese-no-blwf.ttf  ᬓ\u1B44ᬢ\u1B3E  --language=ban
balinese.ttf  ᬓ\u1B44ᬓ\u1B44ᬢ\u1B3E  --language=ban
```

With `blwf`, taling moves to the front of the syllable; without, only to after the adeg-adeg. The trace of the first, through GSUB:

```trace
font: balinese.ttf
text: ᬓ\u1B44ᬢ\u1B3E
options: --language=ban
from: start table GSUB
to: end table GSUB
```

The reordering inserts dotted circles first, before the moves (`reorder_use`, `:448`), into broken clusters, after any leading `R`, as a `B`. At its end it releases `use_category`, and the next pause releases `syllable`.

## Topographical forms

The joining scripts under USE, such as Mongolian and N’Ko, take their `isol`, `init`, `medi` and `fina` masks from the Arabic joining machine, as [Joining scripts](joining-scripts.html#joining-scripts-under-use) describes. For every other USE script, `setup_topographical_masks` (`:232`) sets them by syllable instead. Each syllable that joins is at first isolated; if the syllable before it was isolated or final, that one becomes initial or medial and this one final. A hieroglyph or non-cluster breaks the chain. The masks are set before any lookup, from the first syllables found, and only for those of the four features the font has.

This is HarfBuzz’s own design. The specification says the topographical features invoke forms “based on non-joining or white space boundaries”, and adds: “Support for topographical features for non-joining scripts is not currently implemented in USE. Additional specification is required.”

`deva3.ttf`’s `init` lookup shows it. Under `dev2` the same lookup is the Indic shaper’s `init`, which takes a pre-base vowel sign at the start of a word ([`init`](the-indic-model.html#init)); under `dev3` it takes a whole cluster that another cluster follows:

```shape
deva2.ttf  क\u093F  --language=hi
deva3.ttf  क\u093F  --language=hi
deva3.ttf  क\u093Fक  --language=hi
deva3.ttf  क\u093F\u0020  --language=hi
deva3.ttf  क\u093F क\u093F  --language=hi
deva3.ttf  क\u093F\u2060क\u093F  --language=hi
```

Alone, the cluster is isolated, and the vowel sign keeps its ordinary form. Before another cluster it is initial. It is initial before a space too: a space is a symbol cluster, which joins, so in the fifth line the first cluster is initial and the second final (a form this font has no lookup for), as if the space weren’t there. Only the word joiner, a non-cluster, ends the chain. ZWNJ doesn’t end it either, since it belongs to the cluster before it. For a font that uses `init` or `fina` for word-initial or word-final forms in a non-joining USE script, the edge of a word is the edge of the run (inferred from the code; the specification’s “white space boundaries” suggest otherwise).

## The nine Indic scripts under `dev3`

[Choosing a script shaper](choosing-a-script-shaper.html#the-same-text-in-seven-fonts) showed three Devanagari syllables shaped alike under `dev2` and `dev3`. That is the common case, but not the only one. The same lookups, under the two tags:

```shape
deva2.ttf  क\u094Dत  --language=hi
deva3.ttf  क\u094Dत  --language=hi
deva2-half-first.ttf  क\u094Dर  --language=hi
deva3-half-first.ttf  क\u094Dर  --language=hi
deva2.ttf  र\u094Dक\u0941\u0902  --language=hi
deva3.ttf  र\u094Dक\u0941\u0902  --language=hi
deva2-no-half.ttf  र\u094Dक\u094Dत  --language=hi
deva3-no-half.ttf  र\u094Dक\u094Dत  --language=hi
```

**Lookup order.** KA, virama, RA: the Indic shaper asks `blwf` about RA, finds it below-base, makes KA the base, and runs `blwf` in a stage before `half`, so RA becomes rakar whatever the LookupList says. USE asks nothing. With `half`’s lookup first, KA + virama becomes the half form, and `blwf` then has no virama to match. Under `dev3`, the LookupList order is the font’s shaping logic.

**The reph.** In Devanagari the Indic shaper puts the reph at the end of the syllable, before any anusvara; USE puts it before the first post-base glyph, here the vowel sign U, between KA and its mark. Both orders look the same once marks are positioned, but `abvs`, `blws` and GPOS see a different sequence. And where a virama stays visible, the Indic shaper moves the reph after it (step 2 of its reph rules, [The reph](the-indic-model.html#the-reph_1)); USE stops before it.

The joiners behave differently too:

```shape
deva2.ttf  क\u094D\u200Cर  --language=hi
deva3.ttf  क\u094D\u200Cर  --language=hi
deva2.ttf  र\u094D\u200Dक  --language=hi
deva3.ttf  र\u094D\u200Dक  --language=hi
```

KA, virama, ZWNJ is how a visible virama is written inside a word. The Indic shaper honours it: ZWNJ clears the `half` mask. USE has no `half` mask, the ZWNJ comes after the two glyphs the half form needs, and the half form forms. A font can’t stop it with a lookahead either, since USE’s lookups pass over ZWNJ in their context (read from the code; not tried with a font). RA, virama, ZWJ asks for an eyelash RA rather than a reph. The Indic shaper won’t make a reph when a joiner follows the virama; USE doesn’t look, and makes one. Both look like differences a `dev3` font can’t easily work round (inferred), and Microsoft’s specification doesn’t say how its engine treats them.

Everything the Indic chapter’s [Script by script](the-indic-model.html#script-by-script) table lists is absent under `3` tags, as are the reph positions, the `blwf` modes and the Uniscribe heuristics. A Malayalam dot reph is an `R` and moves like any other reph.

> For type designers: under a `3` tag, the shaper tells your lookups nothing about which consonant is the base. `half`, `blwf`, `pstf` and the other basic features apply to every glyph of the syllable, together, in the order of your LookupList, so their lookups must say themselves, by context and order, where each form belongs. The shaper only moves what your `rphf` and `pref` produced, and pre-base vowel signs, and never past a virama your lookups left standing.

## In short

* USE gives every character one category, derived from Unicode’s Indic syllabic and positional categories, joining types, general categories and default ignorables, with Microsoft’s override files and HarfBuzz’s own changes. ZWJ, CGJ and the variation selectors are invisible to the grammar.
* One Ragel grammar, a single template of base, consonant modifiers, medials, vowels, vowel modifiers and finals in a fixed order, divides the run into nine kinds of cluster. A space is a symbol cluster and can carry marks.
* There is no base consonant and no question put to the font. The basic features apply together, to the whole syllable, in LookupList order; only `rphf` (on the first three glyphs) and `pref` have stages of their own, and what they substitute is recorded as a reph or a pre-base glyph.
* One reordering pass moves the reph forward to before the first post-base glyph, and pre-base vowel signs, modifiers and `pref` forms back to the start of the syllable, neither past an unligated virama.
* Non-joining USE scripts get HarfBuzz’s own topographical forms, cluster by cluster, which spaces and ZWNJ don’t interrupt.
* Under `dev3` and the other `3` tags, Devanagari and its kin follow all of this: LookupList order decides forms, the reph lands earlier, and ZWNJ and ZWJ after a virama don’t stop a half form or a reph.
